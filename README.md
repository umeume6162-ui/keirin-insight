### 引き継ぎ時の確認順

1. 上記の正式仕様書を読む。既存の判定基準を勝手に新設・改変しない。
2. 本番シートの最新受付数・収集済み開催数・レース数、保留・承認済み件数を実際に読み取る。古い数値を確定値として引き継がない。
3. 手動・自動の両方の受付を横断し、同じ選手・レースを重複登録しない。
4. 直近のコード変更・テスト結果・未解決不具合を確認。修理優先、ただし影響のない収集・照合・同期を不必要に止めない。
5. 「3サイト中2サイト一致」の既定基準で必要項目を照合し、対象項目に適したサイトを実績に基づき選ぶ。完了分を同じ理由で延々と再照合しない。
6. 照合合格分は既存の承認・公開ガードと同期契約に従ってサイト反映へ進める。取得・保存・照合合格・正式承認・公開を別々に報告。
7. 手動は自動実行の追加処理。両者で同じ仕様・研究成果・サイト評価を使用する。

**正式な仕様書の改定先は `tools/STAGED_INTAKE_V4.md`。** スプレッドシートの「KI｜引き継ぎ・共通仕様」は入口と要点の控えであり、矛盾した場合は最新版の正式仕様書と実際のコード／台帳を照合して解決する。チャット移行はリセットの理由にならない。

## 検査・テスト運用の整理（2026-11-23）

目的は**照合済みの件数を増やしつつ誤公開を防ぐ**こと。検査実行回数そのものを成果としない。

| 層 | 実行条件 | 残す検査 | 原則実行しないもの |
|---|---|---|---|
| 受付・手動照合 | 新しい証拠を保存する時 | 既存記録との重複、4必須項目/全車全必須項目の2媒体一致、例外と事前ライン、保存→対象行再読 | 変更のない過去全件の再照合、同一URLの無限再試行 |
| 正式フィード更新 | 公開JSONをpushした時 | `tools/check_publication_completeness.cjs`：ID、レースキー、全車結果、ライン、出典・証拠構造、フィード相互整合 | 過去18レース等の研究全件監査 |
| 画面表示 | 現行push/PR・手動検査 | `tools/test_mobile_result_contract.cjs`：HTMLの表示契約と事前並び表示ガードのみ | 上記フィード整合性の重複チェック（2026-11-23に移管） |
| 履歴・例外の回帰 | PR／手動実行、関連スキーマや例外処理の変更時 | 保存済みレースの例外・同着・欠車・重複証拠や発走前整合の深掘り検査 | 通常の選手ID追加ごとの実行 |
| 過去データの監査レポート | 必要な問題の診断時のみ | 研究用read-only監査 | 自動PASS判定・公開条件への昇格 |

重複整理：`check_publication_completeness.cjs`を**唯一の正式フィード整合チェック**とし、`test_mobile_result_contract.cjs`から同内容の全レースループを撤去。表示の由来（発走前予想の根拠）判定は前者へ移管し、表示文字列とレンダリング防御は後者に残す。通常pushはこれまでどおり2検査、歴史的な深い7検査はPR/手動用のまま。安全ゲートは削除しない。

Google Sheetsの旧V76再実行タブは原本と同一内容の重複保管。両方とも歴史証拠として保全し、1件の検査結果と数える。旧テストタブの削除やGASトリガー停止は**本体ソースと参照依存を確認できるまで実施しない**。棚卸は既存`KI｜タブ棚卸`を使用し、重複した管理表を作らない。

同じレースの同じ失敗は**2回で一旦切り替え**、別開催・別日・別情報源へ移る。再開条件と不足項目を既存台帳に保持する。合格済み選手・レースは原則再検査せず、証拠を引き継いで適格分を公開する。実際のCI成功とiPhoneでの実表示はコード保存とは別に確認する。
