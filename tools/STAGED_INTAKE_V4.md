# V4 staged intake workflow

- Save actual source observations promptly in the appropriate restricted intake ledger, with source URL, retrieval method, time, and exact evidence reference or clearly labeled field transcription.
- Never manufacture a source observation from an earlier report or existing result ledger. A transcription is not a retained original.
- Use registration number plus identity fields for rider deduplication, and date/venue/race number for result deduplication.
- Keep one-source observations pending, compare fields independently, and record disagreement or missing values separately.
- Use B+ only for complete official single-source observations with traceable evidence, B for other traceable single-source observations. A/S require independent corroboration and purpose-specific primary sources. These are candidate grades, not approval.
- Do not change official publication or training gates. Pending observations remain restricted; optional exploratory review must be clearly labeled and separated from validated training.
- Prefer new targets and meeting-level comparisons. Preserve old records, avoid duplicate intake, and report verified write/readback counts separately from search results.
- Do not count an existing race as newly collected merely because it is rechecked.
- Existing V3.2 synchronization and publication contracts remain unchanged until a reviewed integration is deployed.

## Shared manual/automatic execution contract

- This document is the common policy for manual chat work and automated tasks. Both must read the latest revision before processing; neither may maintain a conflicting private standard. Record the policy revision used in each execution report.
- Apply identical collection scope (all classes and venues; prioritize A-class seven-rider midnight meetings), source evaluation, field normalization, identity/race keys, evidence grading, missing-data treatment, approval gates and write/readback checks regardless of executor.
- Keep intake channels distinct for provenance, not quality. Before writing, reconcile both channels against existing records; transfer only evidence with its original provenance and never count a duplicate as new. Recheck conflicts and missing fields under the same rules.
- Share source performance observations, verified research findings, pending targets and failures across both execution paths using the existing authorized ledgers and repository workflow. Read the latest shared state at the start of every run; update it after verified work. Do not treat an earlier chat report as evidence.
- Changes to research criteria must be recorded in this common policy (or a referenced versioned rule set), reviewed, and applied prospectively by both paths. Do not silently regrade historical evidence. Report revision mismatches and stop affected writes until reconciled.
- Report acquired, saved, readback-verified, independently approved and published counts separately. A failed write or unavailable source must not inflate any count. Preserve existing task roles and schedules, and the V3.2 synchronization contract; the synchronization-only task must not perform collection or intake writes.

## Defect-first maintenance (manual and automatic)

- When a defect, failed write/readback, unexpected exclusion, inconsistent count, or synchronization fault occurs, prioritize diagnosis and repair over new collection or feature work. Stop affected operations; do not silently skip the fault or inflate progress. Preserve original records and evidence.
- Record the observed failure, reproducible inputs and logs, affected scope, root cause (or explicitly unresolved status), and remediation in the authorized shared workflow. If repair is blocked, report the blocker and keep affected operations on hold.
- Apply a reviewed fix and regression tests, assess historical impact, then retry the affected operation and verify persisted fields by readback. Resume normal affected work only after verification; never bypass approval, provenance, or publication gates.
- Share fixes and regression criteria across manual and automatic execution. Record the policy/code revision and verification outcomes. Preserve existing task roles, schedules, and synchronization-only write boundaries.

## Delivery and continuity priority

- The primary objective is accumulating usable race and rider data, completing established verification and approval, synchronizing eligible results to KEIRIN INSIGHT, and conducting research. Governance and maintenance support that objective rather than replacing it.
- Reuse existing implemented and tested workflows. A chat migration is not a reason to reset criteria, rebuild completed functionality, or introduce new approval requirements. Preserve historical data and existing compatibility.
- Isolate defects to their affected operations; prioritize repair while allowing unaffected collection, verification, and synchronization to continue under existing safeguards.
- Move completed, independently approved and publication-eligible records through the existing synchronization contract promptly. Report any blocked transition and its actual reason; never equate pending intake with completed approval.
- Prioritize verified data throughput and usable research outputs over repetitive status reports or speculative redesign. Do not weaken established evidence, approval, or publication requirements.
